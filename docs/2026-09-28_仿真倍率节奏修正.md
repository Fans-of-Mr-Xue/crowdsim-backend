# 仿真倍率节奏修正

## 修改目的

旧服务循环先计算、记录、构建和发送一帧，再完整等待 `step_length / speed_factor`。实际间隔叠加了计算耗时，导致设置 3 倍不等于实际 3 倍。

现在在 `OverlayServer._run_loop` 使用单调时钟计算本轮已消耗时间：

```
target_interval = step_length / speed_factor
remaining_sleep = max(0, target_interval - elapsed_compute_and_send)
await asyncio.sleep(remaining_sleep)
```

轻负载只等待剩余预算；超时时仍执行 sleep(0)，把执行机会交还事件循环，保证暂停、重置、连接和性能上报等任务可以运行。每步独立计算预算，不累计追赶债务，不因前一步超时而批量补帧。等待开始前读取最新倍率；已经开始的等待不强行中断，倍率变更最迟在后续迭代使用。

暂停分支仍正常等待，不推进或发送仿真帧；正常完成时仍立即退出，无末尾额外等待。

## 不变项

- SUMO 仍以原定 0.5 仿真秒步长推进。
- 人数、寻路、行为、五状态和活动时间均不变。
- 每个推进步骤仍构建/发送一次 update，不跳步、不减推送、不改变前端 15 FPS 插值。
- 没有修改前端倍速范围，也没有把原 pushFps 字段改造成新的限频机制。

## 性能记录

- 新增 `stages.target_step_interval`：完整目标间隔，单位毫秒。
- `stages.requested_sleep`：剩余等待预算，可能为 0。
- `stages.pacing_sleep`：实际异步等待耗时；超时时也保留让出执行机会的耗时。
- `cycle_total` 和实际倍率计算口径保持不变。

旧性能文件没有 target_step_interval，其中 requested_sleep 为完整目标间隔，不能与新记录不加区分地解释。既有 runs 不重写。

例如：步长 0.5 秒、倍率 3，本步计算和发送耗时 50 毫秒时只等约 117 毫秒；耗时 400 毫秒时不再额外等 167 毫秒，理论上该步约 1.25 倍速，但仍不能达到 3 倍。实际耗时还包括调度等开销。

减少等待不等于减少计算量：相同仿真步数的业务日志总量通常不变，但单位墙钟时间的 CPU、发送、磁盘及前端压力可能升高，也不保证降温。

## 验证与使用

`tests/test_websocket_pacing.py` 用可控时钟验证：轻负载扣除计算/构建/发送时间、超时零等待、无追赶补帧、倍率升降、暂停、完成，以及真实事件循环的让出/暂停/恢复/取消。

配合现有性能记录、WebSocket、仿真循环、人口守恒和关闭流程的小型 SUMO 回归测试。输出使用临时目录，不运行纪念塔完整任务。

验证结果：新增 7 项计时测试与现有回归合计 46 项全部通过；`git diff --check` 通过。没有重启用户服务，也没有生成正式 runs 测试记录。

重启后端后生效；前端无需代码更新。建议用上一轮相同的 700 人、3 倍速、相同视角重新运行，比较同阶段的实际倍率、cycle_total、target_step_interval 和 requested_sleep。不要将不同人数或不同聚集阶段直接比较。
