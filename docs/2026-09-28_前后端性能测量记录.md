# 前后端轻量性能测量

## 如何采集

1. 重启后端，刷新前端，沿用正常启动方式。默认启用测量；旧进程不会自动获得新探针。
2. 选择 800 人，保持固定播放倍率（与需要比较的运行一致）和视角，运行一轮。
3. 建议覆盖入场、聚集、离场。若完整运行过慢，至少覆盖明显变慢的聚集阶段；保留 runs，即可先分析局部结果。
4. 电脑放在通风的硬质桌面。不要在运行中刷新/关闭页面，否则原有连接生命周期会结束本轮。

无需开浏览器控制台，不需要逐帧复制数据。每约 5 秒墙钟时间汇总一次，最后不足 5 秒的窗口在完成/重置/关闭时尽力保存。前端只有后端 init 明确声明 measurement enabled 才开始，兼容旧后端。关闭页面时末尾消息不能保证送达，之前保存的窗口不受影响。

## 输出

每轮 `runs/<run_id>/` 新增：

- `performance.backend.jsonl`：Python 后端分阶段耗时、完整循环耗时、实际倍率、Python CPU 时间、发送帧大小。
- `performance.frontend.jsonl`：前端接收解析、帧处理、地图数据处理、插值、Canvas 绘制提交耗时、实际更新频率。
- `performance.system.jsonl`：后续增加的系统 CPU/GPU、相关进程资源、热压力与电池温度，详见[系统资源测量记录](2026-09-28_系统资源测量记录.md)。
- `manifest.json.performance_measurement`：是否启用、汇总间隔与版本。

每行是一段时间窗口，不是某个行人或某一帧。只维护 count/total/mean/max，不保存无限增长的样本数组，不逐人打印。后台会限频并验证前端上报的 run_id、指标名、数值范围与数量；不接受文件路径，不写业务命令日志，也不改变仿真状态。前端发送队列积压超过 64 KiB 时跳过当前上报，避免性能记录进一步挤占队列。每轮允许一次 final 报告绕过常规一秒限频，保留短尾窗。

## 后端指标解释

`stages` 中 count 为调用次数，total/mean/max 为对应单位的总量、均值、峰值，耗时单位为毫秒。

| 指标 | 含义 |
| --- | --- |
| tick_total | 一次完整后端仿真步，含以下多个子阶段 |
| boundary_total | 命令、事件、保持/限速、候选刷新等步前处理 |
| route_context | boundary_total 内的寻路候选与上下文刷新 |
| decision_resolve | 规则/LLM 决策求解 |
| plan_apply_including_log | 单条决策执行及其记录；count 是计划数，不是仿真步数 |
| decision_log | 上述阶段内的决策序列化/日志写入 |
| sumo_step | TraCI 推进一步并取回运动快照，不是 SUMO 进程 CPU 使用率 |
| neighbour_observation | 邻居搜索、密度与观测构建 |
| state_update | 心理/疲劳/邻居状态更新，包括四个显示持续时间计数器 |
| visual_classification | 五状态分类、缓存、计数；不包含 state_update 中的计时器更新 |
| metrics | 仿真指标统计 |
| record_step | 轨迹、指标等逐步记录；不包括 decision_log |
| frame_build | 为前端构建完整帧字典 |
| json_encode | 完整 update 帧的 JSON 编码 |
| websocket_send | await WebSocket send 完成耗时，包括可能的压缩、缓冲/背压；不是端到端网络延迟 |
| update_payload_bytes | 未经 WebSocket 压缩的帧字节数 |
| target_step_interval | 按倍率计算的每步目标墙钟间隔；倍率节奏修正后新增 |
| requested_sleep | 修正后为扣除本步计算、帧构建、编码和发送耗时后的剩余等待；旧记录没有 target_step_interval，requested_sleep 表示未扣耗时的完整目标间隔 |
| pacing_sleep | 实际 await sleep 耗时，可能包含事件循环调度延迟 |
| cycle_total | 从一次 RUNNING 步开始到计算、发送和原有等待结束 |

父子阶段有重叠，不能将所有 total 相加当作总耗时。tick_total 包含 boundary_total；boundary_total 包含 route_context；plan_apply_including_log 包含 decision_log。部分生命周期处理未单独拆分，属于 tick_total 的剩余部分。

`actual_speed_factor = simulated_seconds / running_cycle_wall_seconds`，累计每个正在运行的循环，排除 READY/PAUSED 期间单独等待；最后一步原本不等待，依然保持。requested_speed_factor 是窗口末尾设置。`python_cpu_one_core_percent` 来自 Python 进程 CPU 时间/运行循环墙钟时间，100% 约为一个核；不包括 SUMO、浏览器或 GPU。前后端循环在倍率/暂停切换附近可能跨界，窗口状态均描述窗口末端，不宜用过渡窗做稳态比较。

## 前端指标解释

- json_parse、message_handle：有效 update 帧解析及同步处理；message_handle 包含 frame_normalize 等子阶段。
- update_message_chars：浏览器收到的解压后 JSON 字符数，不是压缩后的网络字节数。
- frame_normalize：帧字段归一化和已有前端效果处理。
- map_normalize：坐标转换、绘制行构建及抽样。
- position_interpolation / position_extrapolation：已有插值/短时外推耗时。
- map_update：地图点/热力数据提交及覆盖层数据准备，不包含此前的 map_normalize/插值。
- canvas_draw：Canvas 清理、投影和点绘制等同步调用的耗时。
- receive_interval、map_interval、canvas_interval：真实调用间隔，含调度卡顿或暂停间隔。
- canvas_updates_per_second / map_updates_per_second：本窗口真实执行更新次数/墙钟秒数，不是设定 15 FPS，也不是显示器实际呈现帧率。
- visible：汇总时页面是否处于前台；后台限频会影响更新频率。
- long_tasks_supported 和 long_task：浏览器支持时记录页面主线程长任务。Safari 可能不支持；false 是不可用，不是“没有卡顿”。
- js_heap_used_bytes：浏览器暴露 performance.memory 时才读取，否则为 null；不是整个网页进程内存。

JavaScript 耗时不包含全部异步 GPU 工作、样式布局、绘制合成和系统窗口开销。初版未采集系统硬件资源；后续新增独立的低频系统采样日志，不能将其整机 GPU 或浏览器进程合计直接视为本页面独占开销。芯片摄氏温度仍不可用，电池温度与热压力不替代芯片温度。

## 不变项与关闭方式

测量初次接入时没有改变人数、规则、五状态阈值、SUMO 步长、原有额外 sleep、推送逻辑、15 FPS 插值或渲染人数上限。随后独立进行了[仿真倍率节奏修正](2026-09-28_仿真倍率节奏修正.md)，将完整额外等待改为剩余预算等待；请按该说明区分新旧性能记录。前端测量仅多一个每 5 秒汇总的定时器，没有额外 RAF 循环。记录写入失败会停用探针，并在 get_status 的 performance.error 中提供原因，不因此终止仿真。

需要对照测量开销时，以 `CROWDSIM_PERF=0 bash run.sh` 启动后端，前端将不启动本轮测量；正常启动默认开启。开关前后应使用相同人数、倍率、设备条件和仿真阶段，不能把两次不同聚集阶段直接相比。

## 实现文件

- 后端：`crowdsim/infrastructure/performance_probe.py`、`simulation_runtime.py`、`websocket_server.py`。
- 前端：`src/utils/crowdPerformance.js`、`crowdSimConnection.js`、`CrowdSimSimulationImmersive.vue`、`CrowdSim3DViz.vue`。
- 测试：后端 `tests/test_performance_probe.py`，前端 `tests/crowdPerformance.test.mjs` 及连接测试。

验证使用临时输出目录和独立小型 SUMO 走廊，不替用户运行 800 人完整任务，不写入正式 runs。完整浏览器联调和 800 人各阶段数据仍需用户运行后确认。

已通过前端 21 项测试（探针聚合、清理、兼容性、连接和组件编译等）、后端 39 项测试（探针、WebSocket、仿真循环、人口守恒和关闭流程）。SUMO 小型对照中开启/关闭探针的 12 步轨迹、速度、五状态和压力状态完全一致。前端生产构建通过，保留项目既有的大包及动态/静态混合导入警告。该对照验证功能一致性，不代表 800 人运行的测量开销已经做过实机基准。
