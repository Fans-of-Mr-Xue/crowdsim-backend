**三、先确定两条顺序：开发顺序和用户使用顺序**

开发顺序建议为：

1. 核清已有方法的输入、输出、局限，选一个最小场景独立跑通。
2. 从可用输出反推必需输入，确定对话与右侧共同使用的数据结构。
3. 接通填写、建议、确认、同步、持久化及再次编辑。
4. 接通领域模型、实验运行、比较与报告。
5. 最后合并重复导航，统一样式并完善演示。

用户看到的主流程建议为：

**提出研究问题 → 澄清范围和预期输出 → 补充必要输入 → 确认整体方案及实验安排 → 整理领域模型 → 运行与比较 → 查看解释和报告。**

这个流程约束助手的职责，不要求用户按固定话术依次回答。用户一次提供多个信息时一起提取；用户改时间就只处理时间；已确认信息不重复询问；未准备齐的数据可以先记录缺口，但正式运行前必须满足所选方法的要求。

**四、对话和右侧需要怎样改**

每轮对话先读取当前任务、已有答案、用户手动修改和待确认内容，再判断当前缺少什么。提问必须能说明“这个答案会影响哪项输入或哪个输出”，每轮只处理一两个关键问题。

建议把常见交互统一为下面几种：

| 用户情况 | 助手行为 | 右侧变化 |
| --- | --- | --- |
| 用户直接给出明确值 | 提取并说明将修改哪一项 | 校验通过后更新对应字段，并显示执行结果 |
| 用户不知道怎么填 | 给一个填写示例，说明需要哪些信息 | 显示待补充状态 |
| 用户请助手推荐参数或分布 | 给建议值、理由、来源和适用限制 | 先作为待确认建议展示 |
| 用户接受建议 | 应用该条建议，不扩大范围 | 写入参数；假设仍标为假设 |
| 用户拒绝或修改建议 | 保留拒绝理由，提出替代方案或修改建议 | 不保留被拒绝的生效值，不反复推荐同一内容 |
| 用户只问概念 | 解释概念并联系当前任务 | 不顺带改配置、保存或跳转 |
| 用户在右侧手动修改 | 下轮以修改后的结构化状态为准 | 不被旧对话覆盖 |

例如用户说“我不知道初始人群怎么分布”，助手可以说明：“可以先按可行走面积分配，或者使用你提供的分区人数。当前模型已支持前一种；如果采用，会把它标成情景假设。是否使用？”不能先悄悄采用，再声称已经确认。

“提供案例”需要区分两件事：一类是**填写示例**，帮助用户表达时间、人数、分布；另一类是**历史参考案例**，提供风险机制和数据依据。前者不自动成为当前任务参数，后者不自动提供当前场景的实测人数。

目前已有字段白名单、页面变化检查、执行回执、草稿保存和历史恢复，继续沿用这条链路。补强重点是：

- 左侧说已经应用的内容，右侧必须能看到；失败时直接显示失败，不给完成提示。
- “已补充需求文字”“已有数值输入”“已保存任务”“已确认方案”“已完成运行”分别显示，不能用一个勾混在一起。
- 模型提出的假设、参数和实验设置也需要可追踪的确认状态。当前案例采纳有专门后端校验，应检查普通建议是否达到同样约束。
- 一次修改多个字段时，清楚说明全部成功、部分成功或未执行；刷新和切换对话后仍保持一致。
- 点击“确认需求”前给出完整摘要，包含目标、范围、输入及缺口、方法建议、实验安排和输出；用户确认后再进入领域模型。

性能方面，会议观察到“发送像没成功”和等待过长。应让用户消息立即进入对话记录，输入框和发送状态清晰，区分检索、生成、应用、保存、失败。当前需求对话每轮都会检索案例，可以按本轮意图减少与简单改日期等操作无关的检索；实际耗时要测量后再优化，不能仅凭转写判断数据库或模型谁是根因。

每个方法应补一份简短能力说明：解决什么问题、需要哪些字段、产生哪些输出、哪些参数生效、是否随机、尚不能说明什么。当前四个内置方法在代码中的含义是：

| 方法 | 当前实现 | 下一步说明与核对重点 |

**六、案例和领域模型怎样调整**

案例检索先按研究场景与风险机制筛选，再结合地点、活动类型、空间特征、可用数据和用户问题排序。纯日期数字相似不算相关；跨场景案例必须能解释具体借鉴机制，否则不推荐。用户只借鉴“瓶颈与双向汇流”，就不能连同历史人数和措施效果一起采用。

每张参考卡片至少说清：来源、相关之处、与本任务的差异、建议借鉴内容、不能照搬的内容。采纳后除了增加引用，还应把相应研究问题或资料需求同步到方案。拒绝、移除、修改借鉴范围都应同步。会议里的500错误和采纳异常需要复测；现在代码已有数据库关键词检索，不能再笼统认定为“完全没有检索”。

领域模型建议用四个主要视角组织，并允许交叉引用：

| 视角 | 应展示的内容 | 要接到哪里 |
| --- | --- | --- |
| 场景与空间 | 实际可用路网、通道连接、宽度、容量、出入口、障碍与开放条件 | 预测网络与地图；后续阶段按约定复用 |
| 人群与主体 | 总量、构成、空间分布、角色、可用行为和感知范围 | 对应的计算参数或主体模板；未接入项单独标注 |
| 规则与方法 | 行走、驻留、路线选择、引导响应、管控等规则 | 具体触发条件、参数和执行方法 |
| 知识与依据 | 资料、案例、外部条件、适用时间及缺口 | 关联到前面哪个参数、规则或判断 |

它应帮助回答“当前任务可用哪些建模资料、哪些已落实、哪些仍是假设”，避免重复一遍需求文本或堆满泛泛的知识卡片。会议提出的跨阶段复用方向，可先落实为路网版本、主体模板、规则来源和任务标识的衔接；不必在这一轮承担事中、事后的全部改造。

路网需要分别核对底图、计算路网、坐标转换与版本，不能只看两张地图是否相似。当前事前后端已有任务路网快照和环境库复用，应以此为基础检查是否与事中使用同一版道路和出口。事前展示密度与时间变化可以沿用二维呈现方式。

**七、补齐实验、结果与报告**

实验安排要在整体方案里说清：选用哪些方法、比较哪些条件、哪些输入保持一致、运行多少次、随机种子怎样设置、统计哪些指标，以及如何处理结果。用户可以接受系统建议，也可以通过对话修改。

当前已有“一组配置下运行多个方法并保存结果”的能力。下一步在此基础上增加实验组，而不是另建一套预测执行链：

- 一个实验组关联固定任务版本、路网版本、输入快照和方法版本。
- 组内记录各次运行、种子或情景差异、排队／运行／成功／失败状态。
- 随机结果展示均值、离散程度及单次结果；方法比较保持同一输入口径。
- 对比时解释差异对应哪些机制或假设。没有观测数据时，只能说明方法差异，不能证明哪个方法更准确。
- 保存配置、结果、分析和报告，方便再次查看；完整仿真回放不是本轮的前置要求。

结果页至少接好“二维空间分布＋时间变化＋方法比较＋关键解释”。报告则应能沿着“结果记录 → 指标变化 → 分析判断 → 建议”查到依据。可以先给用户建议，再展示依据；生成建议时必须先有实际结果与分析。

例如，报告若建议调整某通道，应引用哪次实验、哪个时间段、什么指标暴露了问题。只有已经运行对应对照情景，才能报告措施带来的改善幅度；未试验过的措施标为待验证建议。当前前端仍有静态示例与动态结果两个路径，必须保持显著区分，避免切换任务后仍引用旧案例结论。

**九、建议按这三批实施**

第一批先把最小可用流程做实：选上海人民英雄纪念塔作为演示场景，明确现有方法支持的一个研究问题；核对算法输入输出；收缩需求清单；跑通用户填写、建议确认、右侧同步、保存恢复和整体方案确认。交付标准是用户改一个真实输入，后端能读取，结果能解释相应变化。

第二批完善研判过程：改进案例检索与借鉴；完成领域模型中路网、人群和规则的来源关联；接实验组、方法比较与结果统计；让报告逐条引用实验依据。人群异质性和可编辑空间分布若纳入本轮，应作为明确的算法扩展，分别验收。

第三批整理页面与演示：迁移并合并重复方案入口；统一对话样式和发送状态；按事前、事中、事后隔离历史对话；准备一套可重放的真实演示记录。高亮、排版等在主流程稳定后调整。

**十、验收时直接走这些场景**

1. 用户一次说清地点、时间和目标，助手提取已有信息，只追问关键缺项，不追加审批问题。
2. 用户只改跨年时间，右侧时间同步，其他已确认内容保留；年份不明时才澄清。
3. 用户不会填人数或分布，助手给示例和建议；未同意前不作为生效输入，同意后仍标明假设来源。
4. 用户拒绝一个案例，不采纳、不在下一轮无理由重新推荐；只采纳某机制时，不照搬历史人数。
5. 用户在右侧编辑后继续对话，助手读取新值；刷新、切换历史再回来也一致。
6. 页面已变或保存失败时，界面说明未执行或未保存，不声称完成。
7. 整体方案确认前能看到方法、实验安排、输出和真实缺口；确认研究安排不冒充全部资料齐备。
8. 改变某输入后，可以指出求解器在哪里使用它；尚未生效的人群比例不能包装成已经支持异质性预测。
9. 同一个任务在需求页、领域模型、结果页使用一致路网版本；核对与事中对应场景的路网和出口。
10. 多方法比较使用同一输入快照；随机重复有种子与统计，确定性重复不虚构变化。
11. 报告建议能追溯到本次运行的结果；静态示例不替代真实结果，风险指数不写成事故概率。
12. 示例对话支持自然表达、修正和不懂就问，退出后真实任务保持原状态。

实施前仍需与师兄统一的范围主要有三项：本轮是否真正接入人群异质性；“预测方案”合并后的导航名称与配置位置；领域模型向事中、事后提供哪些共享对象。上述事项不妨碍先完成方法能力核对和对话同步这一批工作。
