## 2. 场地迁移与路网修正

### 2.1 目的地区域及连通性

原陈毅广场单边热点改为纪念塔多边区域，区分环道、纪念塔入口、公园内部、公园入口及外围接近区，并校验道路存在、行人权限、区域关系和可达性。

| 用途 | SUMO 边 ID |
| --- | --- |
| 唯一外环的两个连续边 | `679361567#1`、`679361567#2` |
| M1 西入口 / M2 南入口 | `178411801#0` / `177931018#0` |
| P01 / P11 / P12 / P13 / P14 | `906417851#0` / `906417852#7` / `906417852#8` / `906417852#9` / `906417852#10` |

内侧地面环道 `178411801#1`、`679361566#1`、`177931018#1`，以及四条更深层道路列入 `excluded_edges`；到访、离场和动态改路都不得借用。没有从路网物理删除这些边，也没有为“单环化”修改条带模型。

### 2.2 walking-area 几何死锁

P13/P14 汇入 P15、P16 出口、M1 等处曾出现下游仍有空间但持续停步的问题。按真实连接拓扑识别公园与 M1/M2 相关的 17 个 walking area，通常从 2 m 加宽至 4 m；M1 环道侧 `:6361541057_w0` 采用 5 m。只改 lane `width`，不改 shape、length、ID 或连接关系。

新增 `scripts/validate_hotspot_junctions.py`，每个路口用独立临时需求和 SUMO 进程测试，不启动完整纪念塔任务。按每个有序方向组合 4 人的既定压力，在 `jamtime=3601` 下最终 17/17 通过，最大连续停步 6.4 秒。该结果不保证任意人流规模均不拥堵。

普通 jamtime 调试期曾改为 60 秒，最终恢复 3601 秒；没有采用 3 秒强行解堵方案。直接编辑路网是当前最小修正，重新执行 OSM/netconvert 可能覆盖宽度，后续应将规则固化到生成流程。

## 3. 需求、活动与时间轴

### 3.1 刷新和离场

- 刷新点从较远的园外道路收拢到西侧五条园内道路；按扣除两端余量后的可用长度加权，在边上分层随机分配，保留 2 m 边界余量。
- 已在公园内的行人不再绕行公园南北入口，直接选路进入纪念塔。
- 离场目的边在同一组五条道路间等概率分配，边上位置随机且保留 2 m 余量；与个人原刷新点独立采样。
- 删除热点场景所有背景行人。普通研究场景及旧陈毅广场配置不是本轮“删除背景行人”的全局目标。

### 3.3 集中到达、统一散场、移除开场空等

当前原始时间模板为：到达 240～360 秒占 10%，360～540 秒占 75%，540～660 秒占 15%；活动 600～800 秒，活动结束后 0～90 秒分散释放离场。刷新时间按“计划到达时间 − 精确进场距离 / 1.2 m/s”倒推，最小为 0；1.2 m/s 仅用于排期，不是所有行人的固定实际速度。

最后新增 `align_first_visitor_to_zero=true`：先完成原始路线和全部随机计划，再统一减去最早刷新时间；同步更新刷新、计划到达、活动、个人绝对离场时间及运行期热点元数据，不改变相对时间间隔、人数、位置或路线。

## 4. 寻路与行程安全

- **先修复行程丢失：**动态改路必须保留个人目标边及 `arrivalPos`、后续停留/离场安排；热点采用“目标锁”而非完整路线锁。执行前校验，阶段修改失败时回滚，无法完整恢复时报告部分失败，不伪装成功。
- **再重构精确寻路：**`PositionAwarePedestrianRouter` 区分每条边两端，使用 SUMO 行人连接及内部 walking-area/crossing，计算起终点 offset 对应的部分边距离；不将 M1/M2 或整条环道当成同一点。
- **统一初始/动态/离场：**三类路线共用精确位置模型。入口以通用 `access_portals` 配置，方向自动比较；场地拓扑和禁行区来自配置，不把纪念塔名称写死在核心寻路算法中。
- **保留个体选择：**候选成本结合距离、拥堵密度/速度；画像决定是否值得换路。当前每 10 秒检查、15 秒换路冷却、基础收益门槛 20 秒；进入入口后的承诺约束避免入口内反复掉头。
- **性能设计：**图一次构建，自由流树缓存；同一选路周期共享拥堵快照和动态最短路树。画像不各自建立整套树；提供查询/缓存命中诊断。
- **撤销过度约束：**不再为了避免条带横移而禁止从原入口离场；也不强行把人流按比例分配给 M1/M2。

这仍是模型成本下的最优路线与有限频率的个体换路，不是保证实时全知、任意拥堵下绝对最短的导航。详见[精确位置寻路](position_aware_pedestrian_routing.md)。

## 5. 去除停留瞬移，保留真实空间占用

确认原跳变存在于 SUMO/TraCI 坐标：普通 `<stop>` 进入等待阶段时会将人员移至道路参考线侧方约 3 m，造成视觉上的另一圈；不是前端投影造成。

需求改为两个连续 `<walk>`，不写热点 `<stop>`。后端在到达阶段切换后施加独立 activity hold，最大步行速度保持为 0，直到个人绝对释放时刻再恢复画像速度；始终留在 striping 步行模型中。hold 不被普通继续、拥堵/危险限速意外解除。

区分 `hotspot_approaching`、`hotspot_dwelling`、`hotspot_departing`。计划停留不算被迫堵塞，但仍占用道路并参与密度/风险判定。单人真实 SUMO 验证消除了原约 3 m 的等待侧移；正常转向、条带切换仍可能存在，未承诺所有横向位移为零。

## 6. 指标与五状态

### 6.1 场景指标

扩展核心环道、纪念塔入口、公园内部、公园入口和外围接近区的分区人数、面积、密度、速度、慢行人数、分边统计及入口累计流量。访客生命周期区分待出发、接近、进入、停留、离场与完成。

`HotspotPhaseTracker` 根据测量值确认 `normal → building → congested → dispersing → residual_congestion / cleared`；核心区状态和整体状态分开，外围仍有未完成访客/积压时不能仅因环道空了就报清场。

### 6.2 五状态统一判定

规则来自 `config/crowd_visual_state.json`，按下表从上到下判定：

| 状态/颜色 | 当前条件 |
| --- | --- |
| `high_risk` 红 | 密度 ≥4.0 人/㎡持续 5 仿真秒；或密度 ≥3.5 且速度 <0.2 m/s 两条件同时持续 5 秒 |
| `crowded` 橙 | 密度 ≥1.5 人/㎡，未触发红色 |
| `planned_stop` 蓝 | 热点停留或未到期的计划等待，未触发红/橙 |
| `busy` 黄 | 密度 ≥0.5 人/㎡，或非计划低速持续 5 秒，未触发前述状态 |
| `normal` 绿 | 其他 |

显示计时与行为决策的堵塞计时分离；条件中断即清零，暂停/重复序列化不推进计时。每步统一缓存分类，帧、人数和轨迹复用；记录原因、密度有效性及计时证据，缺失密度不伪装成零。

仍采用既有“同 edge、个人感知半径、2r×可步行宽度”的近似密度，尚未重构固定尺度跨边密度。红色仅为工程风险提示，橙色也不保证绝对不会受伤。详见[五状态记录](2026-09-27_行人五状态显示修改记录.md)。

## 7. 人数配置、生命周期与运行归档

`HotspotDemandSpec` 按每轮 0～10000 人生成需求，服务默认使用配置 700 人。非整数、越界值拒绝；运行中不能扩缩容。同人数重复配置不重建，不同人数需重置；准备状态回执结束前不可开始。

初始化放到工作线程但与仿真操作串行协调；取消时等待准备结束再释放资源。必须替换 SUMO 原行人路线，0 人也替换，防止预设 700 人残留。非零需求继续应用画像速度采样。

每轮 `runs/<run_id>/` 保存输入配置 `hotspot.config.json`、生成需求 `hotspot.generated.rou.xml`、实际需求 `demand.rou.xml`（非零任务）、`demand_generation.json`、manifest、轨迹、指标及生命周期记录。生成报告包含实际人数、种子、配置/需求来源哈希、道路分配与时间信息；当前 `generation_version=2`，保留 `configured_*` 原始值、有效时间和 `timeline_shift_seconds`。

不覆盖历史 runs 或公共静态预生成路线。直接启动静态 `bund.hotspot.sumocfg` 的旧路线不自动获得新生成行为，独立静态实验须重新生成需求；服务入口则每轮生成。详见[自定义人数记录](2026-09-27_自定义热点人数修改记录.md)。

## 8. 仿真节奏与性能测量

### 8.1 倍速节奏

前端最高可请求 3 倍。后端从“计算完再完整等待”改成 `max(0, step_length / speed_factor - 本步计算及发送耗时)`；超时仅 `sleep(0)` 让出事件循环，不累计追赶、不跳步，暂停/完成保持原语义。

这消除无效等待，但不减少每步业务计算量、不保证 3 倍，也可能提高单位现实时间的 CPU/发送/写盘压力。详见[倍率节奏修正](2026-09-28_仿真倍率节奏修正.md)。

### 8.2 三类测量记录

| 文件 | 记录内容与解释边界 |
| --- | --- |
| `performance.backend.jsonl` | SUMO/TraCI、邻居、状态、决策执行/日志、指标、帧构建编码发送、等待预算、完整周期、实际倍率；父子阶段不能简单求和 |
| `performance.frontend.jsonl` | 前端低频汇总的解析、归一化、插值、Canvas 提交时间与可见性；不是全部 GPU 耗时 |
| `performance.system.jsonl` | 整机 CPU、进程组 CPU/RSS、Apple GPU 利用率/内存、系统热压力、电池温度及充电状态 |

约每 5 秒现实时间汇总；系统采样在初始化成功后独立线程运行，READY/PAUSED 也记录，结束/关闭时退出，不调用 TraCI。不为未连接演示页面提前采样。写入失败隔离，不因此终止业务仿真。

整机 CPU 归一化为 0～100%，进程 CPU 的 100% 代表一个核；浏览器/WebKit 组、WindowServer 和整机 GPU 受其他应用影响，不能视为本页面独占。CPU/GPU 芯片摄氏温度不可用，明确为 null；电池温度与系统热压力不能替代。系统采样当前面向 macOS，其他系统显式降级。

### 8.3 修复进程采样缺陷

中文环境 `ps lstart` 字段数量不同，曾导致大量进程遗漏。现仅给 ps 子进程设置 C locale 并使用 `-ww`，校验每行，记录原始/成功/失败行数、后端 PID 是否找到和缺失分组。

区分完整/部分/不可用、首次基线、真实零占用、进程新建/消失、PID 复用和计数回退；不完整组不再冒充完整 CPU/RSS 合计。没有改系统语言，没有旧日志迁移、补录或兼容转换。

测量开关：`CROWDSIM_SYSTEM_PERF=0` 只关系统采样，`CROWDSIM_PERF=0` 关闭整套测量。详见[前后端耗时](2026-09-28_前后端性能测量记录.md)、[系统资源](2026-09-28_系统资源测量记录.md)、[采样修正](2026-09-28_进程采样修正.md)。
